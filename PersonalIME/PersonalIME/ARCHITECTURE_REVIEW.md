# 输入法架构诊断与重构方案

> ⚠️ **历史文档（2026-10-01）**：本文是对**旧架构**（`words.frequency` 单字段 + 15 个档位常量）
> 的诊断记录。该架构已在 2026-10-02 被整体替换：词库改为离线流水线产出的
> `assets/dict/base_words.db`（38.7 万条、连续 logp），数据层拆为
> `base_words`（只读先验）/ `user_words`（不衰减）/ `user_pref`（指数衰减）三层。
> 实测综合 Top-1 由 58.3% 提升到 86.4%，可达率 84.7% → 98.9%。
> **现状与后续计划请看 `../OVERHAUL_PLAN.md` 的「〇、实施进度」。**
> 本文保留仅作问题成因的追溯依据。

> 本文回答一个问题：**为什么打了很久，想要的词还是排在后面？**
> 结论是：这不是几个 bug，而是排序模型的层次缺失 + 词库来源选错了。

---

## 一、结论先行

当前项目的输入→候选链路是这样的：

按键 → T9 数字串 → SQL 查同数字词条 → 按 `frequency` 整数降序 → 显示

整条链路里，**判断"哪个词更该排前面"只用了一个信号：一个手写的整数 `frequency`**。
而这个整数的取值来自七八套互相叠加的档位规则。系统没有语言模型、没有上下文、没有真实概率。

用一句话概括病灶：

> 这是一个"**按档位打补丁**"的排序系统，而不是一个"**按概率排序**"的排序系统。

真实输入法是贝叶斯解码：给定按键序列，在所有可能的字串里找概率最大的那个。
本项目的 `frequency` 想近似其中的 "词频"，但它是**离散档位**、**手工调参**、**覆盖不全**，三件事各自都会引入排序错误。

## 二、为什么「你好」会排在后面（完整链路复盘）

### 实测数据

- 输入 `64426`（n-i-h-a-o 全在 6/4/4/2/6 键）
- 候选栏真实顺序：密函 → 密告 → 拟稿 → 米糕 → 蜜柑 → **你好** → 密竿 → 密耗 ...
- 「你好」的 `frequency` = **50**，而前五个词 = **62**

### 根因

**九键并键**是第一层原因。T9 把 n/m 并到 `6` 键，l/r 并到 `5` 键，于是：

- `ni'hao`（你好）= 64426
- `mi'han`（密函）= 64426

两者数字序列**完全相同**，仅凭按键无法区分。

**词库来源错配**是第二层原因。本项目的 `word_freq.txt`（《现代汉语常用词表》5.6 万词）**没有收录「你好」**，而「密函」「拟稿」「米糕」「蜜柑」这些文言/生造词**反而被收录了**，于是前者停在资产平档 50，后者拿到 62 档。

结果：5 个正常人一辈子不会打的生僻词，把最高频的问候语挤到了第 6 位。

### 这不是个例

同样的机制会导致**所有"口语高频 + 书面语低频"的词**全部排后：
「您好」「不对」「是的」「做什么」「干什么」「什么时候」「好的」「在吗」……实测这些词**全部不在词表里**，全部停在 50 档。

## 三、七个结构性问题

### 问题 1｜没有语言模型，只有一个孤立的词频数字

输入法要解的数学问题是：

```
P(H | D) ∝ P(H) × P(D | H)
        = 语言模型 × 打字模型
```

主流方案在 lattice（候选网格）上用 **Viterbi 动态规划**求全局最优路径。

本项目只实现了最粗糙的一项——**unigram 词频**，而且连它都是离散档位。没有 `P(D|H)` 的概率建模，没有上下文。

**为什么这个缺陷在九键上是致命的：** 全拼输入 `nihao` 只对应「你好」一个词组；九键输入 `64426` 却同时对应「你好/密函/拟稿/米糕…」几十个词。"哪个更像人话"这个判断，**必须靠上下文**（前一个词是什么），孤立的词频在原理上给不出答案。

### 问题 2｜词频是离散档位，不是连续概率

全系统用这些整数近似"常用度"：

```
100(技术词) 95(用户词) 94~91(高频单字) 92(口语词) 90(手编) 89~62(词频分级)
88(常用词/多音字) 85/55(单字) 50/48/46(资产平档) 60(用户组词)
```

**15 个以上的魔法数字**，每个都是为某个具体 case 手工划出来的。

致命的是分辨率：5.5 万个词的 rank 被压进 5 个档（88/84/78/70/62），而 **29.8 万条词（占全库 72%）共用同一个 `50`**。

后果：同音组内大量词并列同分，排序退化成**数据库插入顺序**——用户感觉就是"随机"、"怪怪的"、"我想要的总是靠后"。

### 问题 3｜排序逻辑是补丁堆出来的

代码里散布着为单一场景打的补丁，注释本身就是证据：

- `inputT9` 里手工分三级：tier0 恰好打完 / tier1 已打部分 / tier2 续打匹配
- `displayCandidates` 里把结果手工拼接：`exact + sentences + rest`
- 注释写着"否则会被大量前缀词/高频单字淹没（如 撤退/词 打不出）"
- 注释写着"旧规则'段数优先'曾导致 **给我** 打不出"
- 注释写着"多取一些再截断"、"取 16 时 23.8% 词条打不出，取 60 降至 ~4.5%"

这些都是**用特判去救具体 case**。每加一条特判能修好一个词，但会在别处引入新的失衡——因为底层没有统一的打分函数，只有一堆互相比大小的整数。

**判断标准**：如果换一套词库、换一个档位数值，排序结果就不可预期地变化，那它就不是架构，是调参。

### 问题 4｜词库来源选错了：字典式"求全"，而非语料式"求常用"

实测词库构成（41.17 万条）：

- 单字 7,908
- 两字词 **289,633**
- 三字词 55,570
- 四字及以上 58,182

两字词占了 70%。但打开同音组看到的全是**密函、密竿、密耗、尼干、拟捍、昵好、米泔、麋膏、糜耗、猋急、俵寄**。

这些词的共同点：**在任何真实语料里出现次数都接近 0**。它们来自《汉典》一类"字典型"词库——目标是**收字收词求全**，而输入法要的是**按真实使用频率排序**。

它们的存在有三重伤害：

1. 占掉候选位（用户要翻页）
2. 参与排序、稀释权重
3. 因为被 `word_freq` 收录而拿到比常用口语词更高的档位

**同时另一半是缺失。** 实测专业领域覆盖：

- 计算机/IT：27/40 —— 缺 **微服务、数据结构、多线程、线程池、协程、负载均衡、序列化、内存泄漏、限流、容灾**
- 网络流行语：11/22 —— 缺 **打工人、破防、内卷、直播间、精神内耗、显眼包**
- 职场黑话：13/21 —— 缺 **闭环、颗粒度、拉通、痛点、落地**
- 生活消费：15/20 —— 缺 **蓝牙耳机、扫地机器人、数据线、满减**
- 文学/医学/法律/金融：覆盖较好（19~25/20~26）

### 问题 5｜用户学习机制太粗糙

三个缺陷：

1. **没有时间衰减**。一次点选直接把词频跳到 95（用户保护档）。主流做法是"带衰减地累加"——防止一次误选让某词永久霸榜。本项目是"一次跳顶，永不回落"。
2. **只学"词"，不学"搭配"**。用户打了「谢谢」之后，系统只记住"谢谢"这个词本身，不记得"谢谢"后面常跟什么。真正的学习价值在 bigram。
3. **（已修复）按拼音更新会误伤同音词**。原实现 `WHERE pinyin = ?`，用户选「你好」会把同拼音的「昵好」一起抬进 95 档，从此「昵好」也可能霸榜。

### 问题 6｜整句候选是"假的语言模型"

`sentenceCandidates` 用 DP 把数字串切分成词条组合，打分公式是：

```
score = 段均词频 + n
```

- `+ n`（数字串长度）对同一次输入的所有路径是**同一个常数**，对排序**完全没有作用**——这是一处无效代码。
- `段均词频` 不是语言模型概率。它把每段词频平均一下，无法表达"我是中国人"比"卧室中国人"更像人话。

真实做法：Viterbi 在 lattice 上求 `max P(W1)...P(Wn|Wn-1)`，转移概率来自 bigram。

### 问题 7｜查询与排序耦合

排序的决定因素（limit 取 16 / 60 / 96、三层优先级、边界校验）**硬编码在 SQL 查询和 Kotlin 逻辑里**，分散在 `DictionaryDatabase` 和 `PinyinEngine` 两个类中。

改排序规则要同时动 SQL 和引擎代码。这让任何调优都变成高风险操作。

## 四、主流输入法是怎么做的

### 数学模型（学术界与工业界一致）

```
P(H | D) ∝ P(H) × P(D | H)
```

- `P(D | H)` 打字模型：拼音/按键 → 汉字的映射（多音字、模糊音在这里处理）
- `P(H)` 语言模型：中文序列本身是否像人话

用 **Viterbi 波束搜索**在候选 lattice 上求全局最优路径。

### 语言模型的规模

- **搜狗 / 腾讯 / 微软拼音**：2-gram 或 3-gram，语料来自搜索引擎级数据
- **SunPinyin（开源）**：3-gram
- **Rime**：词库权重 + 可插拔语法模型（八股文 octagram，基于 n-gram 的插件）
- **Google Pinyin / Android PinyinIME**：字符级 bigram（为省内存，精度换空间）

**降维方案参考**：字符级 bigram 只需 7000+ 常用字，模型可压到 50KB 量级——对手机端完全可行。

### 候选排序的三个信号

主流输入法的排序是这三项加权求和：

1. **基础词频**（只读词典，全局 unigram）
2. **上下文搭配**（bigram：上一个词是"输入"，下一个就优先"法"）
3. **用户词加成**（用户自定义词给高权重，保证能进前列）

### 用户词频的两层设计

- **动态词频**：随使用实时调整，**带时间衰减**（久不用的词权重自然下降）
- **用户自定义词库**：手动添加的词，最高优先级，**不衰减**，除非用户手动删除

### 词库来源（以开源的雾凇拼音为例）

分层挂载，按需启用：

- 字表：《通用规范汉字表》8105 字（+ Unihan 4 万字表可选）
- 基础词库：两字词 + 调频
- 扩展词库：小词库，含多音字注音
- 大词库：腾讯词向量（几十万条，部署较慢，按需启用）
- 流行词：搜狗网络新词
- 其他：《现代汉语常用词表》《同义词词林》《新华成语大词典》校对

**关键理念**：*"字典不是越大越多越好，而是要契合使用场景——越大的字典重码率通常越高。"*

### 可直接使用的开源中文词库

- **THUOCL（清华大学开放中文词库）**：IT 16000 / 财经 3830 / 成语 8519 / 地名 44805 / 历史名人 13658 / 诗词 13703 / 医学 18749 / 饮食 8974 / 法律 9896 / 汽车 1752 / 动物 17287，**全部带 TF 词频**，MIT 授权
- **《现代汉语常用词表》**：国家语委，5.6 万词（项目已在用）
- **搜狗标准词库 / 搜狗网络流行新词**
- **腾讯词向量词表**
- **Gboard 中文词库**
- **DomainWordsDict**：68 个领域、916 万词（重型，适合按需扩展）

## 五、重构路线图

按**收益/风险比**排序，建议分阶段推进。

### P0 · 已完成（本次）

- 新增口语高频词兜底档（`oral_boost.txt` + `ORAL_TIER=92`），覆盖词表漏收的问候/应答/口头结构
- 修复词频学习按拼音误伤同音词的 bug（含整句候选逐词学习路径）
- 词频分级由 5 档细化到 8 档，压缩头部区间换取分辨率

**验证结果**：`64426` 候选栏首位由「密函」变为「你好」✅

### P1 · 词库层重建（收益最大，风险最低）

1. **换词库来源**：以「真实语料频次」为准，替换字典式全量词库
2. **引入领域词库**：THUOCL 分层挂载（IT / 医学 / 法律 / 财经 / 饮食…），按需启用
3. **补网络流行语**：搜狗流行词
4. **清洗生僻词**：剔除文言/异体/OCR 噪声词（可加"最低频次阈值"）
5. **词频改连续值**：用真实 TF 或 log 频率，取代手工档位

### P2 · 排序引擎重构（核心）

1. **统一打分函数**：`score = unigram + λ·bigram + 用户加成`，浮点连续值
2. **引入 bigram 表**：`(prev_word, word, count)`，冷启动可用字符级 bigram 控制体积
3. **整句改 Viterbi**：在 lattice 上求全局最优，取代现在的 `段均词频 + n`
4. **消除三级 matchTier 特判**：让打分自然处理"打完的词优先"

### P3 · 用户层

1. **用户词频带时间衰减**（如按天折损），替代"一次跳顶永不回落"
2. **学习 bigram**：记录词→词的转移，实现真正的上下文预测
3. **用户自定义词库**：最高优先级、不衰减

### P4 · 工程

1. **查询与排序解耦**：SQL 只负责"取候选池"，打分全在引擎层
2. **词库分层加载**：核心词库常驻，领域词库按需
3. **可回滚的调参**：打分权重外部化，离线评估再上线
