### 实测结果三：用户偏好行为（阶段 2，`_tools/eval/report_preference.md`）

偏好是**设备端在线学习**，没有离线语料可评；但它的数学行为可以完全离线复现：
给定某数字组的基础 logp 列表，假设用户选了其中第 r 名的词 cnt 次、距今 Δt 天，
算出加成后的新位次。全部 17.4 万个数字组逐组统计：

| 起点位次 | 选 1 次 → 到第 1 名 | 选 3 次 | 选 10 次 |
|---|---|---|---|
| 第 2 名（旧规则恒为 100%） | 70.2% | 75.6% | 83.1% |
| 第 3 名（旧规则恒为 100%） | 50.1% | 59.1% | 68.3% |
| 第 5 名（旧规则恒为 100%） | 28.2% | 39.5% | 47.1% |
| 第 10 名（旧规则恒为 100%） | 9.8% | 20.7% | 24.1% |
| 第 20 名（旧规则恒为 100%） | 2.4% | 10.7% | 13.6% |

**旧规则（二值门槛）无论从第几名、选几次都是 100% 立刻到第 1 名**——因为
加成是无条件 `+40000`，而同组内"第 2 名追到第 1 名"的中位分差只有 **1592 毫纳特**，
40000 是它的 25 倍。一次误触把整组静音 15.5 天（直到衰减跌破阈值才阶跃式归零）：

| 距上次选择 | 7 天 | 14 天 | 21 天 | 30 天 | 45 天 |
|---|---|---|---|---|---|
| 新·仍反超同组第 1 名 | 56.1% | 39.7% | 24.9% | 11.8% | 2.9% |
| 旧·仍反超同组第 1 名 | 100% | 100% | 0% | 0% | 0% |

新规则把"选择即学习"改成了**学习要有分量**：一次有意选择只能改写"近义同音"这类
贴近的竞争，要把一个靠后的词顶上来得真的反复用过它。

### 阶段 4c：无证据词的字符 bigram 链（本轮重点）

**做了什么**：词库 387,593 条里有 **336,479 条（87%）没有任何语料证据**，
它们的分数此前完全由 `P_char(w) = Π p_char(c_i)` 决定——一个**阶 0** 模型，
对词内邻接毫无感知：「保温杯」与「保温北」只要各字字频相近就同分。
现在追加逐边界的**点互信息**：

```
log P_char(w) = Σ ln p_char(c_i)  +  μ · Σ [ ln P(c_i|c_{i-1}) − ln P_uni(c_i) ]
                                       └─ 字符 bigram 链，与设备端同一份 bigram.db ─┘
```

**μ 的实测曲线**（词库规模在解耦后恒为 387,593 条，所以这是纯排序效应）：

| μ | Top-1 | Top-3 | Top-5 | 可达率 | 平均位次 | MRR |
|---|---|---|---|---|---|---|
| 0（旧行为） | 86.2% | 98.2% | 99.2% | 99.6% | 1.46 | 0.920 |
| 0.5 | 86.2% | 98.4% | 99.4% | 99.8% | 1.35 | 0.921 |
| **1.0（采用）** | 86.2% | **98.4%** | **99.4%** | **99.8%** | **1.35** | **0.921** |
| 1.5 | 86.4% | 98.4% | 99.4% | 99.8% | 1.35 | 0.922 |
| 2.0 | 85.6% | 98.2% | 99.4% | 99.8% | 1.37 | 0.918 |
| 3.0 | 79.9% | 96.7% | 98.8% | 99.6% | 1.62 | 0.883 |

取 μ=1.0 的理由：**μ∈[0.5,1.5] 是指标平台**（跨度 3 倍，两端单调回落），
1.0 是平台中心，且语义上就是"PMI 项全额计入"，不是凑出来的数。
实测收益：平均位次 1.46 → 1.35，Top-3/Top-5 各 +0.2pt，可达率 99.6% → 99.8%。

**可达率那 0.2pt 的机制（逐条追过，别想当然）**：多出来的是 `说得好`（`748633426`），
而它**并不在词库里**——它是整句路径组合出来的。被 4c 真正托上来的是**词条 `说得`**：
它无语料证据，纯 unigram 连乘时 logp = −15273，叠加 PMI 后升到 −13708（+1565 毫纳特，
因为「说得」是强搭配），于是它活过了整句 DP 的束宽（`sent_k=3`），再与 `好` 拼成 `说得好`。
也就是说这条收益走的是"**改变中间位置的路径排序，从而改变束内保留哪几条路径**"，
带有束搜索的间接性——不是在给 `说得好` 本身加分。收益真实，但归因要说对。

**踩到的两个坑（都已修，值得记住）**：

1. **不要用"减语料全局均值"来中心化。** 第一版写成 `raw(c_{i-1}→c_i) − mean_logp`，
   μ=1.0 时词库从 387,593 条掉到 223,514 条（**删掉 42% 的词**）——
   常数偏移按字数线性累积，长词被系统性压低，直接跌出 `prune_logp`。
   改成 PMI 形式后偏移消失。
2. **裁剪判据与排序分数必须解耦。** 即便换成 PMI，只要让裁剪去看带链的分数，
   μ 一开照样砍掉 9.8%…42.3% 的词——因为 `prune_logp = -26` 是按 unigram 尺度
   标定的绝对阈值，而链修正会改变尺度。现在：**是否收录只看 unigram，排序才看链**。
   这样 μ 只影响"长尾内部谁在前"，词库规模恒定，改动可归因、可回滚。

**没能做到的（实测否证了原计划的一个假设）**：原计划写"4c 可替代 `structured.txt` 这类枚举表"。
实测**不能**：把 `structured` 权重置 0 后，`struct` 域 Top-1 从 90% 塌到 80%、
Top-3 从 100% 塌到 85%，`time` 域从 86.2% 掉到 82.8%。
原因是字符链只能表达"字串顺不顺"，**表达不了"这个词本身就在高频使用"**：
`星期天` 很常用，但在通用语料里没有独立词条证据，枚举表承载的是真实频次信息，
链模型推不出来。故 `structured.txt` 保留。

### 本轮（2026-10-02 第三段）修掉的三个缺陷

前两个是**项目自身观测工具**的缺陷——比排序问题更危险，因为它们会让人对着错误的数字做决策。

1. **评测器默认库指向陈旧产物**（`evaluate.py: DEFAULT_DB`）
   原默认是 `_data/test_dict.db`：v16 遗留 schema（`words`/`frequency`）、411,715 条、9 月 3 日的产物。
   不带 `--db` 直接跑得到 57.7%，而人会以为"当前水平就这样"。
   改为指向 `assets/dict/base_words.db`——**评测对象必须只有一个真身**。
2. **`--out` 报告在跨盘符时静默截断**（`evaluate.py: rel_to_root`）
   报告是逐行写出的，中途 `os.path.relpath(临时库, ROOT)` 在 Windows 上跨盘符会抛
   `ValueError`，于是报告文件只剩最上面那个标题（42 字节）。因为异常发生在"计算都算完了"
   之后，极易被当成"报告本来就这么短"。已加 `rel_to_root()` 兜住。
3. **用户偏好被 SQL 的 LIMIT 提前截断，导致"选了它却再也不出现"**
   `DictionaryDatabase.query()` 先 `ORDER BY logp DESC LIMIT ?` 再在内存里加偏好分。
   若用户偏好的是一个基础分排在窗口外的词，它根本不在候选列表里，加成无处可加。
   整句候选给每个子串的窗口只有 6 条，最容易踩到。
   修法：新增 `appendPreferredWords()`，先按数字组把偏好词直接从 base 捞回来补进候选集，
   再交给 `mergeUserWords()` 加成（上限 32 个，避免拼出超长 `IN`）。
4. **联想列表的学习功能整体失效**（同类问题的更严重版本）
   `queryWordsByPrefix()` 把**词前缀**传给了按 `digits GLOB` 匹配的 `mergeUserWords()`，
   于是 `digits GLOB '中国*'` 永远匹配不上任何数字串——用户添加的词和学过的高频联想词
   在联想列表里全部静默无效。新增 `mergeUserDataByWordPrefix()`，按 `word GLOB prefix*` 匹配。

### 剩余不达标（3/492 = 0.61%），性质已厘清

- `自习` —— 同键 `仔细` 在语料里确实更常用，属真实语料分布，非缺陷
- `慢` —— `626` 键上 `男/难/满` 确实更常用，**属评测期望与通用词频冲突**
- `星期一至五` —— 长串多段切分，语料里 `星期以至于` 更常见，属 niche 词条

**Top-1 失手的整体性质（已逐条复核）**：其余 47 条 rank-2 案例几乎全是
**真实语料里的同音近义竞争**，不是模型缺陷——
`收到/受到`、`通知/同志`、`中午/终于`、`灰度/恢复`、`意象/一张`、
`璀璨/摧残`、`彷徨/膀胱`、`踌躇/抽搐`、`呢喃/弥漫`；单字类 `和/个`、`小/现`、`少/前`。
这些词的语料频率本就接近或确实相反，**静态词频模型已到天花板**，
只能靠前文区分——而这正是阶段 4a 已经解决的（同一批字在有上文时 Top-1 91.5%）。
结论：**继续调静态权重的边际收益已很低，下一步的收益在"上下文 + 个人化"。**

## 一、结论摘要（先看这段）

当前项目的核心问题不是「某个词的排序不对」，而是**排序模型只有一层**：

> 下表描述的是**重构前**的基线（用作问题诊断）。现状请对照第〇章的实施进度表。

| 层次 | 主流输入法 | 重构前本项目 |
|---|---|---|
| 词条级先验 | 连续概率 / 真词频 | 8+ 套手工档位（整数魔法值） |
| 上下文级 | bigram / trigram 语言模型 | **完全没有** |
| 个人化 | 带时间衰减的偏好模型 | 一次选中即永久置顶，无衰减 |
| 词库 | 多源语料按频次筛选 + 分层挂载 | 单一书面语词典，求全不求常用 |
| 数据分层 | 基础库 / 用户库 / 模型 分离 | **全部混在一张表的一个 `frequency` 字段里** |

其中**最本质的架构缺陷**是最后一条：`words` 表用同一个 `frequency` 字段同时表达「这个字词在汉语里有多常用」和「这个用户有多喜欢它」。两者语义完全不同、生命周期不同、更新方式不同，却被压成一个整数。所有下游问题（排序怪、补丁表越加越多、升级迁移越来越复杂、无法重置用户数据、无法独立更新词库）都是这一条的直接后果。

推荐路线：**先做词库与数据分层（收益最大、风险最低），再做统一打分函数与轻量语言模型，最后做用户模型与端侧模型**。详见第七章路线图。

## 二、现状架构剖析（代码级，基于实际阅读）

### 2.1 分层结构

```
PersonalIMEService (InputMethodService)
    ├── 按键处理 / 数字串维护 / 候选展示 / 上屏提交
    └── 调用 ↓
PinyinEngine (纯逻辑，无 Android 依赖)
    ├── inputT9(digits)              主候选
    ├── inputT9ByPinyin(digits, 读法) 选定读法后的候选
    ├── sentenceCandidates(digits)    整句组合候选
    ├── pinyinSplits(digits)          拼音选择器（读法回显与排序）
    ├── associate(base)               联想
    └── 学习接口（incrementFrequency / learnPhrase / learnUserWord / addWord）
    └── 调用 ↓
DictionaryDatabase (SQLiteOpenHelper, v16)
```

分层本身**是合理的**：引擎与 Android 解耦、DB 访问收敛在一个类里。问题不在分层，在**数据模型与打分模型**。

### 2.2 数据表与索引

```sql
CREATE TABLE words (
    id        INTEGER PRIMARY KEY AUTOINCREMENT,
    pinyin    TEXT NOT NULL,          -- 带音节分隔，如 "ni'hao"
    word      TEXT NOT NULL,
    frequency INTEGER DEFAULT 1,      -- ← 唯一的分数字段，语义被复用
    digits    TEXT NOT NULL DEFAULT '', -- 预计算 T9 数字串
    UNIQUE(pinyin, word)
);
CREATE INDEX idx_words_digits_freq ON words(digits, frequency DESC);
CREATE INDEX idx_words_pinyin_freq ON words(pinyin, frequency DESC);
CREATE INDEX idx_words_word ON words(word);
```

索引设计**是对的**（`digits` 前缀匹配 + `frequency` 降序可全程走索引，免临时排序），这部分工作做得扎实，重构时应保留这个思路。

### 2.3 词库资产（实测体量）

| 文件 | 行数 | 体积 | 作用 |
|---|---|---|---|
| `cn_chars.txt` | 7,908 | 93 KB | 通用规范汉字表单字 |
| `cn_words.txt` | **403,604** | **8.6 MB** | 汉典成语 + 2~4 字词组 |
| `word_freq.txt` | 55,735 | 799 KB | 《现代汉语常用词表》频级名次 |
| `common_boost.txt` | 510 | 8 KB | 手工精选常用词升档 |
| `char_boost.txt` | 369 | 3 KB | 手工单字词频覆盖 |
| `multi_pron.txt` | 70 | 0.6 KB | 多音字补读音 |
| `oral_boost.txt` | 20 | 0.4 KB | 口语高频词兜底（上次新增） |

产物 APK 体积约 **5.6 MB**。运行时词库总量约 **41 万条**。

### 2.4 排序机制（当前的全部规则）

**第一维：匹配层级 `matchTier`**（0 恰好打完 / 1 已打前缀 / 2 续打更长词），升序优先。
**第二维：`frequency`** 降序。
**第三维：词长** 升序。

三段式排序，`matchTier` 优先于词频——这是**正确的**设计（主流输入法的「打完的词置顶」规则），但第二维的 `frequency` 承载了太多互相冲突的语义。

**档位常量清单（全部散落为魔法数字）**：

| 值 | 语义 | 来源 |
|---|---|---|
| 100 | 英文技术词 | `insertTechTerms` |
| 95 | 用户保护档 | `USER_TIER`，选一次即跳档 |
| 92 | 口语高频词 | `ORAL_TIER` |
| 91~94 | 超高频单字 | `char_boost.txt` |
| 90 | 手编常用词 / 短语种子 | `insertTechTerms` / `insertPhraseSeeds` |
| 89/86/83/79/74/70/65 | 真词频 8 档 | `tierForRank` |
| 88 | 精选常用词 / 多音字补读音 | `COMMON_TIER` / `MULTI_PRON_TIER` |
| 62 | 词表榜内保底 | `tierForRank` |
| 60 | 连续上屏组词初始档 | `USER_COMPOSE_FREQ` |
| 46~50 | 资产词组平档 | `cn_words.txt` |

合计 **15 个以上并发档位体系**，且互相之间没有统一量纲。`tierForRank` 用的 89/86/83… 与 `char_boost` 的 91~94、`COMMON_TIER` 的 88 在同一数值空间里竞争，靠注释里的「不许撞档」约定维持秩序——这是典型的**架构熵增**：每修一个 case 就加一张表 + 一个档位常量。

### 2.5 三个典型故障链（用来说明「为什么修补没有尽头」）

**故障链 A：口语词缺失 + 同键生僻词**
`你好`（ni'hao = 64426）不在《现代汉语常用词表》里 → 停在资产平档 50；
`密函/密告/拟稿/米糕/蜜柑`（同 64426）被词表收录 → 拿到 62 档 → 把「你好」压到第 6 位。
→ 修补：新增 `oral_boost.txt`。但词表未收录率达 86%，**这类补丁永远补不完**。

**故障链 B：档位分辨率不足**
5.5 万词的 rank 被压进 8 个离散值，同一个档位内存在大量并列；并列时排序退化为**数据库返回顺序**（即入库序），用户感知就是「随机」。
→ 修补：把 5 档改 8 档。治标；根本解法是连续值。

**故障链 C：个人偏好污染语言先验**
用户误选一次 `昵好`，它就被抬到 `USER_TIER=95`，**永久**压在所有基础词前面，且没有任何机制能让它降下来。用户唯一的自救方式是清除应用数据。
→ 修补：给 `incrementFrequency` 加 `word` 条件（已做）。但「一次即永久」这个模型本身没变。

三个故障链指向同一个根因：**没有统一的概率量纲 + 没有数据分层**。

### 2.6 引擎侧现状评估

平心而论，`PinyinEngine` 里有几处设计**明显高于 Demo 水平**，重构时要保留：

| 现有实现 | 评价 |
|---|---|
| `digits` 预计算 + 前缀匹配 | 正确。天然支持渐进输入/续打，且可走索引 |
| `matchTier` 三段优先级 | 正确，与主流「打完的词置顶」一致 |
| `pinyinSplits` / `rankSplits` 拼音选择器 | **相当不错**。用「该读法下代表字的词频」给读法排序，思路对 |
| `matchesBoundaries` 强制音节边界 | 正确。用了 DP 判可切分性，不是暴力枚举 |
| `sentenceCandidates` 的 K 路剪枝 DP | 骨架对，但打分函数有问题（见下） |

**引擎侧真正的问题**：

1. `sentenceCandidates` 的分数是 `score / segments + n`，其中 `n` 是**输入数字长度**——这是个纯凑参数的启发式，不是概率。两个候选路径的分数**不可比**，且随输入长度漂移。正确做法是累加对数概率。
2. `CANDIDATE_LIMIT = 60`、前缀 16、续打 96、`WORDS_PER_SUB = 6`、`K = 3` 等硬编码散落在 SQL 调用与引擎里，**调一次排序策略要动两处**，且这些数字之间有隐含依赖（注释里写「24% 词条打不出，取 60 降到 4.5%」）。
3. 无模糊音（zh/z、l/n、in/ing）、无简拼（首字母）、无纠错。九键用户对这些的依赖度**高于**全键盘。
4. 联想 `associate` 是「已有词为前缀的更长词」，属于字符串联想，不是上下文预测。

## 三、主流方案调研

### 3.1 商业输入法（搜狗 / 百度 / 微信）

**架构：级联式多模型流水线**

1. 规则与编辑距离粗筛（混淆矩阵：x↔sh 0.72、r↔l 0.78、s↔sh 0.63 等，毫秒级）
2. N-gram 打分排序，过滤低频干扰
3. 深度语义模型**仅对 Top-K 重排**（reranking）
4. 个性化模型调整

**词库分层**：基础词库 / 专业细胞词库 / 用户词库 / 热词库；搜狗细胞词库截至 2015 年约 3 万个词库、5000 万词条，按 `.scel` 格式在线下载更新。

**端侧轻量化**：新一代版本走「端侧小模型 + 云端大模型」混合，保证隐私与低延迟。

| 优点 | 缺点 |
|---|---|
| 效果上限最高（有万亿级语料与云端算力） | 闭源，无法直接借鉴实现 |
| 分层 pipeline 设计思想完全可借鉴 | 云端方案有隐私争议与延迟 |
| Top-K 重排大幅降低深度模型成本 | 需要语料与训练闭环，个人项目不可复刻 |

**对本项目的借鉴点**：① **级联 + Top-K 重排**这个结构；② 词库分层；③ 混淆矩阵做模糊音。

### 3.2 Rime / librime（架构范式，最值得抄）

**核心是管道架构**：

```
Processors（处理原始按键）
  → Segmentors（把输入流切成语段）
  → Translators（查词典，产出候选）
  → Filters（排序、过滤、置顶、简繁转换）
  → 候选列表
```

**关键组件**：
- Schema 用 YAML DSL 定义（Speller / Translator / Dictionary / Punctuator），**改输入方案不用改 C++**
- 静态词典用 **marisa-trie**（压缩前缀树），用户词典用 **LevelDB**
- 有 Spelling Algebra（拼写代数）：用 `xform` / `xlit` / `derive` 规则生成变体拼写（模糊音、简拼、方言）
- 插件式扩展：自定义 Processor/Segmentor/Translator/Filter 动态加载

| 优点 | 缺点 |
|---|---|
| 管道解耦极彻底，扩展点清晰 | C++17，重写成本对 Kotlin 项目很高 |
| 配置驱动，方案可迭代不用重编译 | YAML + 拼写代数有学习曲线 |
| 词库用户自己维护，生态活跃（rime-ice 等） | **学习/调频能力弱**（用户词快速遗忘，见 3.3） |
| trie + LevelDB 的存储选型成熟 | 九键支持依赖前端（仓输入法/元书），生态碎片 |

**对本项目的借鉴点**：① **管道化**——把「查候选」和「排序」彻底解耦，用 Translator + Filter 两个角色组织；② marisa-trie/DAT 的词典结构选型；③ **拼写代数**思想做模糊音/简拼。

### 3.3 libime / SunPinyin / libpinyin（N-gram 路线）

fcitx 作者对这几套引擎的评价原文（很有参考价值）：

- **libpinyin**：bigram 模型。缺点：早期数据质量差（默认选择有大量错字错词）、**多次随意 break ABI**。
- **SunPinyin**：trigram 模型，但**输入历史会被快速遗忘**，且原生不支持多词库。
- **libime**（fcitx5 新引擎）：沿用 SunPinyin 的 trigram 算法，但用 **kenlm 二进制格式**存储，同样效果下**内存占用更小**；可外挂任意数量词库；支持内模糊切分（`xi'an` vs `xian`）。
- 反面教材：fcitx4 自带拼音是最大前向匹配（不比 20 年前智能 ABC 强）；libgooglepinyin 是 unigram，无上下文预测。

**kenlm 的工程数据**（对手机端选型最关键）：
- 支持 1-5 gram，词级与字符级均可
- mmap 按需加载 + trie/探测哈希 + SIMD 查询
- 实测：中文 3-gram，`.arpa` 8 GB → `.bin` 1.2 GB，加载从分钟级降到秒级
- 中文常用字约 7000 个，**字符级模型**是移动端的常见选择

| 优点 | 缺点 |
|---|---|
| trigram 对整句预测明显优于 bigram | 模型体积大（需量化/剪枝） |
| kenlm 格式成熟，内存可控 | 训练需要大规模语料 |
| 多词库挂载友好 | libpinyin 数据质量与 ABI 有历史问题 |

**对本项目的借鉴点**：① **字符级 n-gram**（而非词级）是手机端的正确起点；② kenlm 的格式与量化思路；③ **多词库挂载**设计。

### 3.4 九键（T9）专用方案

这是本项目**最相关**的一类，单独展开。

**(a) 万象拼音（rime_wanxiang）——当前最成熟的 Rime 九键实践**

三个核心设计：

1. **双路并行编码**：后台同时生成「全数字编码」和「全字母编码」。用户击键产生数字编码唤出模糊候选；前端左侧展示所有可能拼音组合（**拼音选择器**）；点选某个拼音后，系统用精确字母编码替换数字编码 → 候选质量**瞬间等同于 26 键**。
   → 核心价值：把「九键长句盲猜」这个不可解问题，转化成「用户一次点选确定读法」这个可解问题。

2. **零派生转写引擎**：传统 Rime 九键为做简拼会写大量 `derive` 规则，产生**海量废码派生**拖垮字典检索导致卡顿。万象只用最小集合：
   ```
   derive/^(.*)$/\U$1/                          # 复制并转大写
   xlit/ABCDEFGHIJKLMNOPQRSTUVWXYZ/22233344.../ # 大写字母一对一转数字
   ```
   简码需求交给独立的 super replacer 组件，杜绝编码指数级膨胀。

3. **自学习上下文预测与调频**：Lua 组件替代原生 librime-predict，学习用户行文习惯，语境契合的词自动跃升首位，最终可「无脑空格上屏」。

**(b) 薄荷输入法 T9**：`t9.schema.yaml` 基于全拼方案构建，**与全拼共用同一套词库**（`rime_mint`）。这是很重要的一个决策：九键不需要单独词库。

**(c) 论文《Chinese Pinyin Input Method For Mobile Phone》**（很老的论文，但结论对 T9 依然成立）：
- 用**字符级 bigram**（而非词级）——虽然精度略低，但体积小得多
- **标量量化压缩 68%**，性能影响很小
- **直接汉字选择**：跳过「先选拼音再选字」，直接从按键直接推汉字，击键数 4.2 → 3.3
- modeless 界面：用无效输入键做候选索引，消除模式切换
- 结论：字符级模型在手机键位上解码准确率 76%，词级可达 93%，**精度换体积的取舍是必要的**

**(d) 中文 T9 的固有困难（数据）**：`shi` 覆盖 127 个常用字，`si`/`xi` 各超 80 字；T9 中 `zhi/ci/si` 全归 9 键、`n/m` 全归 6 键、`l/r` 全归 5 键。实测单次输入平均产生 **42.7 个候选**。这解释了本项目为什么需要 `CANDIDATE_LIMIT = 60`。

| 优点 | 缺点 |
|---|---|
| 双路编码 + 拼音选择器是九键的**唯一可靠解** | 需前端配合（点击回填），纯输入法 Service 内实现要自绘 |
| 零派生映射性能好，老设备也流畅 | 依赖 librime 生态 |
| 与全拼共用词库，维护成本低 | 自学习调频是 Lua 实现，移植需重写 |

**对本项目的借鉴点（最高优先级）**：
1. **九键不应单独维护一套词库**——和全键盘共用，`digits` 只是索引。
2. **拼音选择器是九键的核心交互**。本项目已有 `pinyinSplits`/`rankSplits` 的雏形，应该升级为正式的一等公民，并支持点击回填（等价于 `inputT9ByPinyin`，这个方法**已经存在**）。
3. **避免派生爆炸**：本项目用「预计算 digits 列 + 前缀 GLOB」已经天然避开了 Rime 的派生爆炸问题，这个设计**优于**传统 Rime 九键方案，应保持。

### 3.5 Gboard / SwiftKey（端侧神经 + 联邦学习）

**Gboard 的数据（非常有用，作为预算基准）**：
- 早期英文主 LM：Katz 平滑贝叶斯插值 **5-gram，125 万条 n-gram，含 16.4 万 unigram**
- 神经版：**CIFG-LSTM，670 单元，1.4M 参数，10,000 词词表**，TF-Lite 端侧推理
- **响应约束：用户期望输入事件后 20 ms 内看到键盘响应**
- **模型预算：通常限制在数十 MB 量级，词表数十万词**
- 联邦学习：只上传加密梯度；一轮上传 **50-100 KB**；典型 cohort 500-5000 设备；差分隐私 ε≈1-2
- 效果（Google+CMU，CHI 2015，词错误率）：

  | 条件 | WER |
  |---|---|
  | 无语言模型 | 38.4% |
  | 仅空间模型 | 15.2% |
  | 空间 + 通用语言模型 | 5.7% |
  | 空间 + **个性化**语言模型 | **4.6%** |

  → 语言模型把错误率从 1/3 降到 1/17；个性化再降约 1.1 个百分点。
  → 另一组数据：个性化模型相对静态模型，**击键节省提升 9.9%**。

**SwiftKey**：端侧个人 LM，从输入文本 + 联系人 + 日历 + 关联账号构建；支持最多 5 种语言同时预测。

| 优点 | 缺点 |
|---|---|
| 效果上限最高 | 训练闭环（联邦学习基建）个人项目无法复刻 |
| 有明确的延迟/体积预算可作为设计约束 | 神经模型在低端机上仍有成本 |
| 联邦学习 + 差分隐私的隐私设计值得学 | 需要大量真实用户数据 |

**对本项目的借鉴点**：① 用 **20 ms 响应**和**模型体积预算**作为硬约束来设计；② 个性化收益是**可量化且显著**的（4.6% vs 5.7%），值得投入；③ 但**不要**在当前阶段做端侧神经模型。

### 3.6 用户词频动态调整（可直接落地的算法）

**指数时间衰减**（业界通用）：

```
Weight(t) = e^{-λ·(t_now - t_last)}
```

上周频繁输入的词，权重显著高于三个月前——既适应变化，又不被旧习惯绑架。

**遗忘因子递推**（实现最简单，推荐）：

```python
def update_weight(code, selected, alpha=0.7):   # alpha = 遗忘因子
    current = user_profile[code][selected]
    decayed = current * alpha                    # 旧偏好打折
    user_profile[code][selected] = decayed + (1 - alpha)  # 本次行为加分
```

**专利 CN102346560B 的显式公式**（用于把「词频 + 时间」合成一个排序分）：

```
M = N / [(T1 - T2) × X] + Y

M  = 当前场景排序词频    N = 词库记录的总词频
T1 = 当前时间            T2 = 最后一次输入该词的时间
X  = 衰减系数（0<X<1，衰减周期通常 1-2 小时）
Y  = 该词的默认词频
```

**全局与个人模型的加权融合**：

```
Score(w) = α·log P_global(w) + (1-α)·log P_personal(w)
```
初值 α = 0.7（偏向通用），随使用时长 α 递减（越来越懂你）。

**搜狗的三个记忆模块**（分工清晰，值得照搬）：
- **词频记忆**：动态调整，久不用会降权（对应衰减）
- **用户词库**：用户主动添加，**优先级极高且持久，不随时间衰减**
- **联想记忆**：记词与词的共现，预测下文

> 关键洞察：**「用户主动添加的词」和「系统学出来的偏好」必须是两种东西**。前者不衰减、可手动管理；后者要衰减、会遗忘。本项目现在把两者都塞进 `frequency`，这是模型层面的根本缺陷。

| 优点 | 缺点 |
|---|---|
| 实现简单（一个乘法 + 一个加法） | 衰减参数 λ/α 需要调，且因人而异 |
| 显著改善「老词霸榜」 | 需要存时间戳 → 表结构要改 |
| 有专利/论文背书，不是玄学 | 跨设备同步时时间戳语义复杂 |

## 四、候选方案设计与对比

给出四个方案，从保守到激进。

### 方案 A：保守修补（继续加补丁表）

**做法**：维持现有架构，继续扩充 `common_boost` / `oral_boost` / `char_boost`，按用户反馈逐个补词。

| 优点 | 缺点 |
|---|---|
| 改动面最小，风险最低 | **不可持续**：词表未收录率 86%，补不完 |
| 可立刻上线 | 补丁表越多，档位冲突越难维护 |
| 不动引擎，回归风险低 | 不解决「档位分辨率」与「上下文缺失」 |
| | 每个新用户都会遇到没补过的 case |

**结论**：**否决**。这就是过去几个版本在做的事，边际收益已趋近于零。

### 方案 B：换词库 + 连续词频（数据层重构）

**做法**：
1. 词库换为组合源：常用口语词表（按语料频次）+ THUOCL 领域词 + rime-ice 校对过的词表
2. 词频从「整数档位」改为 **`REAL` 类型的对数概率** `logp`
3. 一张表拆成三张：`base_words`（只读）/ `models`（只读）/ `user_words`（可写）
4. **砍掉全部补丁表与档位常量**（15 个魔法值归零）
5. 清洗生僻词：按语料频次阈值裁掉「密竿/密耗/尼干/拟捍/昵好/米泔/麋膏」这类真实语料几乎不出现的条目

| 优点 | 缺点 |
|---|---|
| **收益最大、风险最低**——不碰引擎排序主链路 | 需要构建一次词库流水线（离线脚本） |
| 一次性消灭补丁表、档位冲突、升级迁移复杂度 | 词库许可需逐个核对 |
| 数据分层后，词库可独立更新、用户数据可独立重置 | 需要设计新表结构与迁移路径（老用户数据） |
| 词频分辨率从 8 档 → 连续值，同频并列问题消失 | 排除了「用户偏好」，所以不会立刻改善个性化体验 |
| 体积可控（清洗后 41 万条预计可降到 15-25 万条） | |

**结论**：**强烈推荐作为第一阶段**。

### 方案 C：连续词频 + 轻量语言模型 + 统一打分函数（推荐主体）

在 B 的基础上：

1. **统一打分函数**（所有分数在同一量纲 `log` 概率下相加，不再有魔法数字）：

   ```
   Score(c) = w_u · logP_uni(w)
            + w_b · logP_bi(w | prev)
            + w_t · logP_typo(digits | pinyin)     // 纠错/模糊音代价
            + w_s · userScore(w)                    // 用户偏好（带衰减）
            + w_p · matchTierBonus(c)               // 打完的词置顶
   ```

   权重 `w_*` 用一个**小规模回归/网格搜索**在评测集上拟合，而不是拍脑袋。

2. **语言模型分级投入**（按性价比）：
   - **第一优先：候选级重排（reranking）**。只在候选生成后，对同一 `digits` 组的 Top-K（如 20 个）用 bigram 重排。**不改候选生成逻辑，风险极低，收益直接**。
   - **第二优先：字符级 bigram**。7000 常用字，剪枝 + 标量量化后体积约 1-3 MB（论文实测量化可压 68%）。
   - **第三优先：整句 Viterbi**。把 `sentenceCandidates` 的 `score/segments + n` 换成累加 `logP`，与主流做法对齐。

3. **九键专属：按键级打分**。这是本项目相对全键盘输入法的**独有收益点**：数字键到字母是一对多，应在打分里显式建模「该数字串下各拼音的合理性」，而不只是「拼音到词的词频」。

4. **拼音选择器升级为一等公民**（借鉴万象拼音）：候选区左侧常驻读法列表（现有 `pinyinSplits` 已具备），点击即调用现有 `inputT9ByPinyin` 精确过滤。

| 优点 | 缺点 |
|---|---|
| 根治「排序怪」——从「档位比拼」变成「概率比较」 | 工作量大：动引擎排序主链路 |
| 上下文预测解决九键并键歧义（`ni'hao` vs `mi'han`） | bigram 需要语料与训练脚本 |
| 权重可通过评测集拟合，不再靠猜 | 需要先建评测集（否则无法验证） |
| 保留并增强了现有的正确设计（digits 索引、matchTier、拼音选择器） | 冷启动性能与内存需重新评估 |
| | 后续调权重需要纪律，否则又会退化成魔法数字 |

**结论**：**推荐作为第二阶段（主体）**。

### 方案 D：端侧神经语言模型

**做法**：TensorFlow Lite / ONNX Runtime Mobile 部署小型 CIFG-LSTM 或 tiny Transformer，词表 10k-50k。

| 优点 | 缺点 |
|---|---|
| 效果上限最高（可做语义级预测） | **训练数据没有**——没有用户输入语料构建闭环 |
| 上下文理解能力强 | 体积/内存/耗电成本显著 |
| | 推理延迟难以保证 20 ms |
| | 无法解释、难调试，与本项目当前成熟度不匹配 |
| | 联邦学习基建（隐私、聚合、差分隐私）完全不可复刻 |

**结论**：**当前阶段否决**，但应在架构上**预留接口**——即打分函数的 `w_*` 体系应能容纳一个「神经模型打分项」，将来模型替换时不用重写引擎。这是架构设计要考虑 3 年后的事。

### 4.5 选型矩阵

| 维度 | A 保守修补 | B 词库+连续词频 | C +语言模型 | D 端侧神经 |
|---|---|---|---|---|
| 收益 | 低（趋零） | **高** | **很高** | 理论上最高 |
| 风险 | 极低 | **低** | 中高 | 高 |
| 工作量 | 小 | 中 | 大 | 极大 |
| 是否解决「排序怪」 | 否 | 部分 | **是** | 是 |
| 是否解决「词库少」 | 否 | **是** | 是 | 是 |
| 是否解决「生僻词霸榜」 | 否 | **是** | 是 | 是 |
| 是否解决「个性化差」 | 否 | 否 | **是** | 是 |
| 可维护性 | 持续恶化 | **大幅改善** | 改善 | 需专业团队 |
| 建议 | 否决 | **先做** | **再做** | 预留接口 |

## 五、推荐目标架构

### 5.1 分层设计

```
┌─────────────────────────────────────────────────────┐
│ 表现层  InputView / CandidateBar / PinyinSelector   │
│         （候选展示、读法选择、翻页、上屏）              │
└─────────────────────────────────────────────────────┘
                         ↓ 调用
┌─────────────────────────────────────────────────────┐
│ 引擎层  Pipeline（借鉴 librime 的管道思想）             │
│  ① DigitSegmentor   数字串 → 候选音节切分（含分隔符）    │
│  ② CandidateTranslator  切分 → 候选（查 base 词典）     │
│  ③ Scorer          统一打分函数（uni/bi/user/typo/tier）│
│  ④ Reranker        Top-K 重排                        │
│  ⑤ Filter          去重、置顶、数量截断               │
└─────────────────────────────────────────────────────┘
                         ↓ 调用
┌─────────────────────────────────────────────────────┐
│ 模型层  UnigramModel / BigramModel（只读，mmap 加载）   │
└─────────────────────────────────────────────────────┘
                         ↓ 调用
┌─────────────────────────────────────────────────────┐
│ 数据层  base_words（只读） │ user_words（可写） │ user_pref │
└─────────────────────────────────────────────────────┘
```

**关键：③④⑤ 必须独立于 ②**。现在 `inputT9` 一个方法里同时做了查询、合并、打分、截断，改任何一处都会牵连其它。拆开后，排序策略可以单独迭代、单独评测。

### 5.2 数据 schema 设计

```sql
-- ① 基础词库（只读，随包分发 / 可独立更新）
CREATE TABLE base_words (
    pinyin TEXT NOT NULL,        -- ni'hao
    word   TEXT NOT NULL,
    digits TEXT NOT NULL,        -- 64426
    logp   REAL NOT NULL,        -- log 概率（连续值，取代整数档位）
    flags  INTEGER DEFAULT 0,    -- 位标记：成语/人名/地名/专业词/英文
    PRIMARY KEY (digits, word)
);
CREATE INDEX idx_base_digits_logp ON base_words(digits, logp DESC);

-- ② 语言模型（只读，单独文件 mmap 更佳）
CREATE TABLE bigram (
    w1     TEXT NOT NULL,
    w2     TEXT NOT NULL,
    logp   REAL NOT NULL,
    PRIMARY KEY (w1, w2)
);

-- ③ 用户词（可写，用户主动添加 —— 高优先级、不衰减）
CREATE TABLE user_words (
    pinyin TEXT NOT NULL,
    word   TEXT NOT NULL,
    digits TEXT NOT NULL,
    added_at INTEGER NOT NULL,   -- 时间戳
    PRIMARY KEY (pinyin, word)
);

-- ④ 用户偏好（可写 —— 衰减型，与用户词分离）
CREATE TABLE user_pref (
    scope  TEXT NOT NULL,        -- 'word' | 'pinyin' | 'bigram'
    key    TEXT NOT NULL,        -- word 本身 / pinyin / 'w1>w2'
    weight REAL NOT NULL,        -- 当前权重（读取时按 Δt 衰减）
    t_last INTEGER NOT NULL,     -- 最后更新时间戳
    cnt    INTEGER NOT NULL,     -- 累计次数（用于区分"偶发"与"习惯"）
    PRIMARY KEY (scope, key)
);
```

**这个 schema 的三处关键改动**：

1. **`base_words` 只读且与用户数据分离**。用户学习不再修改基础词库 → 词库可整包热更新（下载新文件替换），不会与用户数据冲突；用户数据也可一键重置而不影响语言模型。
2. **`logp` 是连续的 `REAL`**，取代 15 个整数档位。加任何新数据源都只是「写一个 logp」，不再需要「找一个不撞档的魔法数字」。
3. **`user_words` 与 `user_pref` 分离**，对应搜狗「用户词库不衰减 / 词频记忆会衰减」的成熟结论。

### 5.3 统一打分函数（核心设计）

所有分数统一到 **自然对数概率** 量纲，加权相加：

```
Score(c | ctx, digits) =
      w_u · logp_uni(c)
    + w_b · logp_bi(c | prev_word)          // prev_word 来自已上屏上下文
    + w_c · logp_bi_char(c[0] | prev_char)  // 字符级兜底（无词级 bigram 时）
    + w_t · typoScore(digits, c.pinyin)     // 模糊音/纠错代价（≤0）
    + w_s · userScore(c, now)               // 用户偏好（已衰减）
    + w_p · tierBonus(c)                    // matchTier：打完置顶、用户词置顶
    + w_l · lenPrior(c)                     // 词长先验（抑制超长串）
```

设计要点：

1. **所有权重是同量纲可比的线性权重**，可用评测集做网格搜索/逻辑回归拟合，**不靠注释约定**。
2. **`userScore` 内置衰减**：
   ```
   userScore = log(1 + cnt) · e^{-λ·(now - t_last)}
   ```
   `cnt` 让"反复选择"比"偶尔选择"更稳；指数项让旧习惯自然退场。λ 建议按「半衰期 7-14 天」反推。
3. **用户主动添加的词走 `w_p` 的置顶项**（不衰减），而不是参与 `userScore`。
4. **`typoScore` 承载模糊音**：把 zh/z、ch/c、sh/s、n/l、in/ing、f/h 等做成混淆代价表，直接降低对应路径的分数。这对九键用户收益很大（九键本来就把这些并键了）。
5. **打分函数可插拔**：将来神经模型只需实现一个 `logp_nn(c|ctx)`，加一个 `w_n` 项即可，不改引擎。

### 5.4 九键专属设计（本项目差异化重点）

| 设计 | 说明 | 现状 |
|---|---|---|
| **拼音选择器** | 候选区常驻读法列表，点击精确过滤 | 已有 `pinyinSplits`/`rankSplits` + `inputT9ByPinyin`，**升级为一等公民** |
| **双路编码** | 数字编码 + 字母编码并行，选读法后切换为字母编码 | 部分具备（`inputT9ByPinyin` 已下推 DB） |
| **按键级概率** | 建模 `P(拼音 \| 数字串)`，而非仅 `P(词)` | 缺失，是最大空白 |
| **同键歧义消解** | 用 bigram 上下文区分 `ni'hao` / `mi'han` | 缺失 |
| **共用词库** | 九键与全键盘共用同一套词，`digits` 仅作索引 | **已具备**，优于传统 Rime 九键 |
| **无派生爆炸** | 预计算 `digits` 列 + 前缀匹配，无 Rime 式 derive 规则 | **已具备**，应保持 |

> 值得注意的是：本项目在「避免派生爆炸」和「九键共用词库」这两点上**已经做出了优于传统 Rime 九键方案的设计**。重构时**不要丢掉**这两个优势。

### 5.5 性能预算（以 Gboard 的公开约束为基准）

| 指标 | 预算 | 依据 |
|---|---|---|
| 单次按键 → 候选可见 | **≤ 20 ms（p95）** | Gboard 公开的响应约束 |
| 单次按键 DB 查询次数 | ≤ 3（现为 3-5 次：exact + 逐长度 exact + prefix） | 可合并为一次区间查询 |
| 冷启动词库就绪 | ≤ 2 s（后台预热） | 现有 `warmUp()` 思路正确 |
| 语言模型体积 | ≤ 5 MB（bigram 剪枝+量化后） | Op-Ngram 论文：剪枝 + Stupid Backoff 可显著压缩 |
| 总包体积 | ≤ 8 MB | 现 5.6 MB，留 2.4 MB 给模型 |
| 常驻内存 | ≤ 40 MB | 现未测，需先建立基线 |

**必做的性能改造**：
- 候选查询**合并为一次 SQL**（现有 `inputT9` 会依次查 exact(60) + 逐前缀 exact(16) + prefix(96)，最坏 8 次；应按最长数字串做一次区间查询后内存切分）
- 引入**结果缓存**（LRU，按 `digits` 键），回退/连续输入时直接命中
- 语料/模型加载走 **mmap**（Android 可用 `FileChannel.map` 或资产只读副本）

## 六、需要建立的基础设施（先做这个）

**没有评测集，上面所有方案都无法验证，重构会变成新的猜谜。**

### 6.1 评测集（最优先）

构建一个**可重复运行的排序质量评测**：

1. **测试语料**：300-1000 条真实场景句子（聊天、办公、技术、文学各若干），人工标注断句与拼音。
2. **跑法**：把每条句子的每个词独立走一遍 `inputT9(digits)`，检查目标词是否在候选第 1 / 3 / 5 / 10 位。
3. **指标**：

   | 指标 | 含义 | 现状 | 目标 |
   |---|---|---|---|
   | Top-1 命中率 | 首选即目标词的比例 | 待测 | ≥ 85% |
   | Top-5 命中率 | 5 个以内可选中 | 待测 | ≥ 97% |
   | 平均候选位次 | 目标词的平均排名 | 待测 | ≤ 1.4 |
   | 词条可达率 | 输入数字串能出候选的词占比 | 声称 ~95.5% | ≥ 99% |
   | 平均选词键数 | 每输入一个词的击键数 | 待测 | ≤ 3.5 |
   | 整句命中率 | `sentenceCandidates` 首位即正确的比例 | 待测 | ≥ 70% |

4. **回归门禁**：任何改动前跑一遍，指标不得下降。

### 6.2 词库构建流水线（离线脚本）

一次性脚本，输出可直接打包的资产文件：

```
① 收集源：常用词表 + THUOCL(领域) + rime-ice(校对) + 口语词表 + 维基 n-gram 语料
② 归一：拼音标准化（统一分隔符）、繁简统一、异形词合并
③ 注音：无注音词条用最大匹配 + 词频加权补注音
④ 计频：用真实语料算频次 → 转 logp（连续值）
⑤ 清洗：裁掉语料频次低于阈值的生僻词（密竿/密耗/尼干/拟捍/昵好 等）
⑥ 覆盖校验：对评测集的每个词确认在库
⑦ 输出：base_words 资产 + bigram 模型文件 + 统计报告
```

第 ⑤ 步是解决「生僻词霸榜」的**根治手段**——不是靠升档压制它们，而是**直接裁掉**。

## 七、分阶段路线图

### 阶段 0：建基线与评测集（前置，必做）

- **产出**：评测脚本 + 测试语料 + 现状指标快照 + 性能基线（启动耗时/单键延迟/内存/包体积）
- **改代码**：否（只加测试与脚本）
- **验收**：能一键输出 Top-1/Top-5/平均位次等指标
- **风险**：低

### 阶段 1：词库与数据层重构（推荐先做）

- **产出**：新 `base_words` 表（连续 `logp`）+ 词库流水线 + 清洗后的词库
- **改代码**：`DictionaryDatabase` 重写；`PinyinEngine` 仅改 `frequency` → `logp` 的读取
- **砍掉**：`common_boost` / `oral_boost` / `char_boost` / `multi_pron` 四张补丁表与全部档位常量（15 个魔法值归零）
- **验收**：Top-1 ≥ 80%，词条可达率 ≥ 99%，生僻词（密函/拟稿/米糕）不再进前 5，包体积 ≤ 8 MB
- **风险**：低（不动排序主链路）；**主要成本在词库流水线与许可核对**
- **收益**：一次性解决「词库少」「生僻词霸榜」「补丁表失控」「升级迁移复杂」四个问题

### 阶段 2：用户模型分层 + 衰减

- **产出**：`user_words` / `user_pref` 分表；`userScore` 带指数衰减；用户词不衰减
- **改代码**：学习路径重写（`incrementFrequency` / `learnPhrase` / `learnUserWord` 三合一为统一接口）
- **验收**：误选一次的词不会永久霸榜（7 天后自然回落）；常打词仍能稳定置顶
- **风险**：中（涉及所有上屏路径）
- **收益**：解决「个性化越用越糟」「无法重置用户数据」

### 阶段 3：引擎管道化 + 统一打分函数

- **产出**：`Segmentor / Translator / Scorer / Reranker / Filter` 五段拆分；`Score()` 统一实现
- **改代码**：`PinyinEngine` 结构性重构
- **验收**：功能与阶段 1/2 等价（无回归）+ 单键延迟 ≤ 20 ms；排序参数集中在一处，可独立调参
- **风险**：中高（动主链路）
- **收益**：可维护性质变；为语言模型接入铺路

### 阶段 4：轻量语言模型（分三步）

- **4a 候选重排**：只对同一 `digits` 的 Top-K 用 bigram 重排。**不动候选生成**，风险最低、收益明显
- **4b 字符级 bigram**：7000 常用字，剪枝 + 标量量化，体积 ≤ 3 MB
- **4c 整句 Viterbi**：替换 `sentenceCandidates` 的 `score/segments + n`
- **验收**：Top-1 ≥ 85%；整句命中率 ≥ 70%；模型体积 ≤ 5 MB；延迟不超预算
- **风险**：中（需要语料与训练脚本）
- **收益**：根治九键并键歧义与整句预测

### 阶段 5（可选，远期）：模糊音 / 简拼 / 纠错 / 英文混输

- 混淆代价表（zh/z、n/l、in/ing、f/h）接入 `typoScore`
- 简拼（首字母）用独立通道，**不要**用 Rime 式 derive 规则（会导致派生爆炸）
- 英文与中文混输：与技术词表统一到同一打分空间

### 阶段 6（远期，仅预留接口）：端侧神经模型

- 架构上只需新增一个打分项 `w_n · logp_nn(c|ctx)`，引擎不动
- **不实现**，除非将来能构建训练数据闭环

### 9.1 许可风险（**必须逐项核对，这是最容易出事的地方**）

| 中文维基语料 | 维基许可 | 需署名 + 保持相同许可；**注意衍生模型的分发条款** |

### 9.2 技术风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 老用户数据迁移 | 升级后丢用户词 | 阶段 1 设计迁移脚本：从旧 `words` 表按 `frequency >= USER_TIER` 抽出用户词 → 写入 `user_words` |
| 词库流水线一次成型难 | 可能反复调 | 先建评测集，用数据驱动迭代 |
| 打分权重过拟合 | 评测好、实际差 | 评测集与调参集分离 |
| bigram 体积超预算 | 包体积膨胀 | 剪枝（只留高频对）+ 标量量化（可压 ~68%）+ 只对 Top-K 用 |
| 冷启动变慢 | 体验退步 | 后台预热 + mmap + 首屏用精简词库 |
| 又一次退化成魔法数字 | 重蹈覆辙 | **纪律**：所有常量必须集中定义 + 有注释依据 + 有评测支撑 |

### 9.3 架构风险

- **不要一次全上**。方案 C 动主链路，必须等阶段 0/1/2 稳定后再做。
- **不要在重构中丢掉已有优势**：`digits` 预计算索引、`matchTier` 置顶、拼音选择器、`matchesBoundaries` 的音节边界校验——这四处是现有代码里最扎实的部分。
