# PersonalIME 输入法评测方法论

> 这份文档回答一个问题：**「输入法好不好用」到底该怎么量化测？**
> 结论是三条腿走路——国标口径、学术界基准、用户侧效率指标，
> 外加一层最关键的**归因分层**。全部可离线复现，脚本在 `_tools/eval/`。

---

## 零、先说清楚：为什么不能只看 Top-1

「你好排第一没？」这类问法有两个致命问题：

1. **Top-1 只覆盖"能打出来的词"里的一部分**，而且是被挑出来的那部分。
   人工语料挑得出来，往往因为它本来就在你脑子里。真机上真正让人烦躁的是
   「这个词我敲了半天没出现」。
2. **排序问题和词库问题长得一模一样，但药方相反。**
   词库里没有的词，怎么调权重都救不回来；词在库里却排不动，补一万条词也没用。
   不把这两层拆开，优化就是在盲调。

所以本项目的评测体系先解决分层，再谈指标。

## 一、三套指标来源（不是自创的）

### A. 国标：`GB 18031-2000` / `GB/T 19246-2003`（数字键盘汉字输入）

这是**唯一直接针对数字键盘（九键 T9）**的国标，正好命中本项目。

| 指标 | 国标要求 | 含义 | 我们怎么算 |
|---|---|---|---|
| 平均码长 | 逐字 < 6 键/字；字词混合 < 4 键/字 | 打个字平均要敲几下键 | 数字串总长 ÷ 目标字总长 |
| 重码字词键选率 | 拼音 < 6% | 有多少字需要额外按选键才能打出来 | 目标词不在首位(需翻页/点选)的字数占比 |
| 首屏候选命中率 | ≥ 85%（检测机构口径） | 首屏能不能直接看到目标词 | 目标词落在前 5 个候选的比例 |

重码字词键选率这条尤其重要——它就是用户口中的「这个字它老选不对」的量化版本。

### B. 学术界：`PD / P2C` 基准（Zhang et al. 2019；ACL 2022 `PinyinGPT`）

中文拼音输入法事实上的公开评测口径，数据来自人民日报语料，按领域切成
games / culture / sports / realestate / medical / finance 等 15 个 domain，
并按 **上下文长度 × 目标词长** 分格统计：

- 上下文长度：前 0-3 / 4-9 / 10+ 字
- 目标词长：1-3 / 4-9 / 10+ 字
- 指标：P@1 / P@5 / P@10

**参照线**：Google IME 在该基准 Top-1 约 **57%**（ED 子集）/ 70.9%（PD 子集），
On-P2C(bi) 71.3%，GPT(ours) 73.2%，PinyinGPT-Concat 约 76-80%（长上下文 + 整句时更高）。

我们此前只有 492 条**无上下文**的人工语料，缺了上下文维度——
而真实使用中用户是一边看着已上屏文本一边接着敲，
同一串数字里选哪个字常常"没有上文根本无从判断"。这是最大的口径缺口。

### C. CHI / 文本输入研究（Soukoreff & MacKenzie 2003；MacKenzie 2007）

通用文本输入绩效指标：WPM、KSPC（击键/字符）、CER / NCER / TER、MSD-ER、AdjWPM。

其中 **TER（总错误率）** 被公认为最强——它既算"写错了没改"也算"写错了改了"，
连改错误的付出一起计。我们把它落地成一个更容易解释的变体：

**期望击键数 EK =（基础击键 + 选键/翻页/重输成本）÷ 目标字数**

Top-1 告诉"对不对"，EK 告诉"累不累"。手感好不好看后者。

## 二、归因分层（本套评测的核心）

每个样本先落到四层之一，再分别看指标：

| 层 | 定义 | 排查手段 | 对策 |
|---|---|---|---|
| **L1 词库缺失** | 这个词在 `base_words` 里根本不存在 | 按 word 直查词库 | **只能补词**。调任何排序权重都是零收益 |
| **L2 候选不可达** | 词在库里，但它的数字串在两条引擎路径上都说不出它 | `inputT9` 与 `sentenceCandidates` 都查无此词 | 修解码/分词边界，或补同音词条 |
| **L3 位次落后** | 能拼出来，但排在前 5 之外 | 有 rank 且 rank > 5 | 调排序权重 / 上下文重排 |
| **L0 首屏命中** | 正常（≤ 前 5） | — | — |

**为什么必须分层**：阶段 4c 时我们差点把 `structured.txt` 这类手工词表
归咎于"字符链不够"——实测才发现 `中国二手车城` 这类长词**有**语料证据、根本不走字符回退分支。
不分层，每次调参都在给错误的对象调。

## 三、测试集怎么造（`build_testset.py`）

人工语料（`corpus.tsv` 492 条）继续留着当**回归门禁**——它可控、能解释、
改一处参数能立刻看出回退；但它的覆盖窄、带主观性，不能当"整体水平"的度量。

大基准测试集从**真实语料自动化生成**：

1. 用 `_tools/lm/corpus/` 里三个来源 ≈ 4500 万字的语料：
   `news`（新闻 300K）、`spoken`（影视字幕）、`wiki`（百科）
2. **没有现成分词器**，于是用 `base_words.db` 自己本身做最大正向匹配分词——
   分词结果天然就是「输入法自己眼里的一段话」，比外部分词器更贴合评测目标
3. 从真实句子里抽 `(前文上下文, 目标词)` 对，按
   **语料来源 × 目标词长 × 上下文长度** 三层配额轮转抽样，避免全挤在语料开头几句
4. 输出 `bench.tsv`，全文真实、带上下文、上万条

**这一条自带一个循环论证，必须认账**：第 2 步用 `base_words.db` 自己分词，
于是抽出来的「目标词」**必然**都是词库里的词——L1（词库缺失）那一层天然测不出来，
跑出来是 0 条也不奇怪，不能当成「词库覆盖没问题」的证据。

补一个外部交叉验证（一次性核对，结论记在这里）：

- `_data/wf.txt`（55,708 个中文词，与词库无关的第三方词频表） → 不在词库的只有 **3 条**
  （`一二·九运动` `卡拉ＯＫ` `阿Ｑ`，全角/半角混合的特殊写法）
- `_data/freq_words.txt`（56,037 条带拼音词表） → 不在词库的 **3 条**，同上类型

两条独立来源都指向同一个结论：**常用词覆盖已经到位，L1 不是主要矛盾**。
此后若再动这个词库，L1 的判定依然要靠这两份外部表复核，不能只看 bench.tsv。

**踩过的坑（已写进脚本注释）**：`news300k.tar.gz` 里排第一的 member 是
`inv_w.txt`（词频倒排索引，纯数字三列），取最大也取到它——于是读到 43 万行数字、
分词命中 0、**样本池安静地保持 0**，脚本照常跑完、照常出报告，只是 news 那一路
一个样本都没有。现在改成按内容探测（读前 8KB 看汉字占比 > 5%），真正命中的是
`sentences.txt`。

## 四、脚本与用法

```bash
# 1) 生成大基准测试集（几分钟，取决于语料扫描量）
python _tools/eval/build_testset.py --per-cell 260 --out _tools/eval/bench.tsv

# 2) 跑大基准评测
python _tools/eval/eval_bench.py --out _tools/eval/report_bench.md

# 3) 原来的人工语料回归门禁（改动前后各跑一次，指标不得下降）
python _tools/eval/evaluate.py --out _tools/eval/report.md
```

判定规则（建议写进 CI）：

- 国标三条里「首屏候选命中率」未达 85% 就报警；
- 三层归因里 **L1 占比上升** = 词库退化的信号，优先补词；
- 只有 L3 变化才是排序模型的改动生效，L1/L2 变化与排序模型无关。

## 五、评测器复现的是哪条真实路径

`eval_bench.py` 复用 `evaluate.py` 里的引擎复现，与 Kotlin 侧逐条对齐：

- 词条路径：`PinyinEngine.inputT9()`（精确命中 → 最长前缀 → 前缀 GLOB 续打，三段候选）
- 整句路径：`PinyinEngine.sentenceCandidates()`（数字串切词组合，DP 保留每位置 K 条）
- 上下文重排：`CTX_BETA_PER_MILLE=1600`，用上一上屏文本的末字作探针
  （与 `PersonalIMEService.contextCharBeforeCursor()` 一致）
- 打分单位统一为**毫纳特**（自然对数 × 1000），整数除法与 Kotlin `Math.floorDiv` 对齐

**纪律**：评测所用的词库 md5 必须等于打包进 APK 的词库 md5，否则报告里的百分比
跟设备上的真实行为对不上（这条在 `MEMORY.md` 里是硬规矩）。
